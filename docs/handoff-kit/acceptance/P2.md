## 0. 结论前置

P2 v1 **完成**，版本 **0.3.0**。U0–U4 里程碑全部落地；prompt-first 闭环
（生成 → 复制新会话开场提示词 → 新会话 `handoff_load`）在浏览器 UI 上实测；
篡改批次判 `invalid`、漂移批次判 `stale`、只读动作零写入均已取证。
已知缺口如实列于 §7（工作台 root 作用域会话回退、血缘不单列、无删除 UI、中文 v1、
权限错误的 UI 实链未单测替代实测）。

**未改动**：P0/P1 工具 API、`manifest@2`、证据模型与 P0/P1 验收记录；UI 不复制
manifest 解析/校验逻辑（仍只有 `src/manifest.js` 一份）。

## 4. U2 载入 / U3 工作台（浏览器实测）

- 「载入」Tab：批次列表（默认自动选中最新）→ 详情展示 `trust=verified`、`0 error/0 warn`、
  漂移=无、H0/H1 摘要、包内指针、下一步；旧批次 `20261022T075656Z-43ff` 显示
  `trust=stale` + 漂移数字与 findings。
- 详情动作：**复制开场提示词**（成功）与**插入输入框**（面板关闭、提示词进入 composer
  draft，用户核对后未发送）。
- 「工作台」页：左批次列表 + 右详情（复用同一 DetailView）+ 顶部 刷新/校验/生成/继续交接/
  返回对话；「生成」从工作台打开同一浮层面板。
- **继续交接**：append 默认承接最新批次，显示基准批次/写入根目录；点击「确认写入（append）」
  后写出 `batchId=20261022T113405Z-78e8`、真实目录、`第 N 代` 徽章；「查看该批次」选中并校验。
  update 模式要求**二次确认**（黄色提示 + 再点「确认写入（update）」才写盘），本次按要求在
  二次确认处取消、未真写。
- 修复缺陷：工作台是 root 作用域、无会话绑定，Host 曾回退到"最新 live 根会话"而落到其它项目
  （实测显示 `项目 desktop · 0 批次`，后为 `stand` 的 1 个批次）。修复为：Client 在点击
  「交接」时写 `localStorage` 会话 hint；Host 依次尝试 显式 sessionId → 最新 live 根会话 →
  部署目录，并对失效 sessionId 同样回退。修复后工作台正确显示
  `项目 dsh-plugins · 5 个批次 · 会话 session-bd55b217…`。

## 5. L1–L3 验收

### L1 生成 → 提取开场提示词 → 新会话 load 得 trust

- UI 生成 `20261022T112055Z-e27c` 后立即复制开场提示词：文本含 `信任判定：verified
  （哈希与漂移检查通过）`，`pointers`（HANDOFF.md/manifest.json/SHA256SUMS/session evidence）与
  `next` 完整（用户粘贴原文入库）。
- **新会话消费（实测通过）**：用一个**全新上下文会话**（独立 session，不带本会话历史）按开场
  提示词消费最终批次 `20261022T131930Z-6922`，21:20:41–21:20:50 的 `handoff_load` 回执：
  `trust=verified`、`counts: 0 errors / 0 warnings`、`drift: gitHeadChanged=false /
  sourceFilesChanged=0 / sourceFilesMissing=0`、`pointers: 4`、`warnings: 0`、verify findings 无
  （独立复核 HEAD=`1c19eb4b00d7…` 未变、6 个 artifact 哈希全对）。
- **随后出现的真实漂移（如实记录）**：写本验收记录后（`docs/handoff-kit/acceptance/P2.md`
  本身就在批次 `manifest.files` 记录里，sha256 `54c18c6d…`→`ab22e0d4…`），再验同一批次变为
  `trust=stale (0 errors, 1 warning)`，finding=`SOURCE_FILE_CHANGED:
  docs/handoff-kit/acceptance/P2.md`。这是**正确漂移检测**，不是缺陷：包记录 docs 哈希，
  任何后续文档编辑都会被检出。因此"生成时 verified"的证据以上述带时间戳的回执为准；
  若 P3 需要一枚"交付即 verified"的最终包，应在文档冻结提交之后**最后生成一次**且不再编辑
  引用它的文档（见 P2-G7）。

### L2 漂移 / 篡改 / 权限

- 漂移：旧批次 `43ff`/`da0b` 在 UI 显示 `trust=stale` + 漂移数字/findings（实测通过）；
  `78e8` 生成后又改了 UI 源码，再验显示 `trust=stale (0 errors, 1 warning)` +
  `SOURCE_FILE_CHANGED`，"trust 不是生成时快照"由此得到正反两面证据。
- **篡改（实测通过）**：受控复制批次 `20261022T120000Z-dead`（复制 `78e8` 后仅追加一行注释）
  经新会话 `handoff_load`/`handoff_pack verify`：`trust=invalid`；verify `FAILED (2 errors,
  8 warnings)`，错误码 `ARTIFACT_HASH_MISMATCH`（HANDOFF.md：manifest 记录 `1576e87a…` vs
  实际 `5369454d…`）与 `SHA256SUMS_MISMATCH`；其余 6 个 artifact 哈希均匹配。UI 用同一 trust
  徽章组件渲染 invalid（徽章颜色/文案单测覆盖）；验证后该临时样本已删除。
- 权限不足：错误码映射（`HANDOFF_READ_ONLY`/`HANDOFF_SANDBOX_DENIED` 等）有单测；
  P0 已用真实只读/workspace-write 会话验证工具侧拒绝路径。**P2 未在 UI 上跑真实权限拒绝**
  （需切换会话权限），作为已知缺口（P2-G6）。

### L3 只读零写入 / 无网络 / 契约不变

- **只读零写入（实测通过）**：对 `$DSH_HOME/handoff` 全部 49 个文件做 `sha256+size+mtime`
  快照（含 5 个既有批次 + 篡改样本）；用户完成载入/详情/校验/复制/插入等只读动作、并再次
  经 UI 生成最终验收批次后复测：**Changed=0、Missing=0，Added=7**——新增的 7 个文件正好是
  最终批次 `20261022T131930Z-6922` 的 `HANDOFF.md/SHA256SUMS/manifest.json/evidence/*`。
  即：只读动作没有任何写入；唯一的写入来自用户显式点击「生成」。
- 网络：Client 只有 `fetch('/api/handoff-kit/rpc')` 同源调用；无外部网络、无子进程、无 LLM
  （源码可复查：`client.js` 无 `XMLHttpRequest/WebSocket`，`src/ui.js` 仅 `ctx.connection.fetch`）。
- 契约：`git diff` 只含 Client half/UI 桥/版本号/测试/文档；`src/tool.js`、`src/manifest.js`
  未被改动，`src/service.js` 无 P2 改动；P0/P1 单测全绿。
- 写操作确认：生成/继续交接均需显式点击并显示目标根目录；`update` 二次确认。

## 7. 已知缺口

| ID | 缺口 | 处置 |
|---|---|---|
| P2-G1 | 工作台 root 作用域：本页从未点过「交接」时，Host 会话回退可能选中其它项目 | 已缓解：localStorage 会话 hint + Host "最新 live 根会话"回退；点一次「交接」固定；P3 可加项目选择器 |
| P2-G2 | 列表/详情不单列血缘序号 | 接受：不改 P1 load 契约；lineage 在 H0 摘要与 create/append 结果可见 |
| P2-G3 | UI 文案仅中文、未接 locale 服务 | v1 决策；P3 再评估 i18n |
| P2-G4 | 无删除/归档 UI | 宿主无删除原语；沿用 GAPS 手动归档 runbook |
| P2-G5 | 新增 `dsh.client` 声明后需重启 Desktop 一次 | 工具链边界；重启一次后 client 改动可 HMR 热更 |
| P2-G6 | 权限不足未在 UI 实链实测 | 错误码/修法有单测；P0 已真实权限验证工具侧；UI 端以单测 + P0 证据替代，P3 可补 UI 权限矩阵 |
| P2-G7 | 包内证据覆盖 `docs/`，验收记录等文档编辑会让"最后生成的批次"真实漂移；且模型可见文本摘要（1–3 行）不渲染 findings/drift/pointers 明细 | 接受：前者是正确漂移检测（自指记录问题，见 §5 L1），需要"交付即 verified"时在文档冻结提交后最后生成一次；后者沿用 P1-M1-G3 的指针式设计，UI 已用结构化字段完整展示，模型侧需自行复算/读 HANDOFF，不改 P1 渲染契约 |
